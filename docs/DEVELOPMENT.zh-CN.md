# VChat iOS 开发流程

**一个能独立验收的改动一个提交，相关提交一起做云端验证，需要装手机时再出 IPA。** 本项目的目标是让 iPhone 直接用 VCP 服务。迁移桌面功能时，除非需求明确依赖桌面，否则以手机独立使用为验收条件。

## 在哪里做

| 地点 | 适合做的事 |
| --- | --- |
| VPS（同时运行 VCP 服务） | 拉取源码、修改文件、看差异、Git 操作、检查少量配置和日志、查询 Actions 状态。对真实插件只做少量、串行的只读请求。 |
| GitHub 托管运行器 | 自动化测试、无头浏览器、重复渲染、大样本回归都放在云端。Xcode 编译和 iPhone 模拟器测试用 macOS 运行器；网页交互测试可在云端 Linux 上用合成数据运行。 |
| 开发者的 Mac / iPhone | 有 Mac 时可复用同一工作目录和模拟器做增量构建。通常用模拟器验证；涉及锁屏恢复、蓝牙音频、相机或发热时，把需要真机验证的场景写进 PR，按节点集中测试。 |

VPS 不做需要持续或高峰 CPU 的工作：不在上面编译、跑无头浏览器、跑全量测试、做压力测试，也不注册成自托管 CI 运行器。云端缺 Mac 时等待或用自己的 Mac。云端测试不用生产聊天密钥、日记或消息；真实接口只核对状态和必要的字段，不把用户数据带进截图、日志和测试样本。

## 从需求到试用

1. **先写验收场景，再动代码。** 从 fork 最新的目标分支开工作分支。迁移桌面功能时，也取所需桌面模块的最新源码，在 PR 记录参考的提交号。把需求写成能观察的结果，例如：“未发送的草稿在手动收起键盘后还在”。
2. **小提交，集中推送。** 同一功能的实现和对应测试放在一起；不相关的修复可单独回退。准备好一组相关改动再推送、开 PR，不为每个本地提交排一次 Mac。文档单改走独立文档分支；往已有代码 PR 补一行文档，GitHub 仍可能按整个 PR 的差异再跑一次。
3. **按改动选云端测试。** 改键盘，用 UIKit 验证按钮发送、回车发送、手动收起保留草稿；改场图，用合成数据验证触控、查询及慢响应，再用 iOS 模拟器验证 WebKit 原生桥。模拟器应用、测试宿主和依赖必须使用同一目的地和兼容架构。Intel Mac 的模拟器用 x86_64，Apple 芯片 Mac 的模拟器用 arm64；真机 IPA 单独选 iOS 设备目标。两者即使同为 arm64，也不是同一平台的产物。
4. **审查最新提交。** 看代码差异、GitHub 审查意见和最新提交对应的检查。报告分别写清“编译”“模拟器启动”“测试”“IPA”“真机”的结果；一项成功不能代替下一项。失败时先读第一个出错步骤及对应日志。没分到运行器，可以稍后重试同一提交；有编译、链接或断言错误，先修原因再重跑。没有 IPA 可能只是前面的测试失败，并非打包本身坏了。
5. **只在准备装机时安排出包。** 选一个通过相关测试的提交，把已验证的功能合在一个试用版本里。记录提交号、Actions 链接、测试结果和 IPA 下载入口。模拟器 App 不能装到 iPhone；未签名 IPA 需要签名后才能安装。没有真机时明确标注，不因此阻塞只需模拟器就能验证的功能。

**如何出包：** 以目标分支的 [native.yml](../.github/workflows/native.yml) 为准。使用分离流程（见 [PR #1](https://github.com/Huanghgj/vcpchat-ios/pull/1)）时，代码 PR 的 native 任务只跑模拟器；需要试用时，在 GitHub Actions 的 Native iOS Build 页面点击 **Run workflow**，选择对应分支或标签，核对提交号。手动任务只跑 **Package iPhone release**。下载成功运行里的 **VChat-iOS-unsigned**，解压获得未签名 IPA。旧分支若仍在同一次 PR 检查中构建 IPA，直接复用该次产物。

查看本 fork 的 [Actions](https://github.com/Huanghgj/vcpchat-ios/actions) 或 [PR](https://github.com/Huanghgj/vcpchat-ios/pulls)。排队、缺机器和检查失败都不是通过；拿到新提交的实际结果后再更新结论。
